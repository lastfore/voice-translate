# 阶段关键日志增强测试文档

> **对应方案：** [阶段关键日志增强方案.md](./阶段关键日志增强方案.md)  
> **版本：** v1.0  
> **日期：** 2026-07-29  
> **目标：** 为每个开发 phase 提供完成即测的用例，并定义全 phase 完成后的整体验收用例。

---

## 1. 测试范围

- 覆盖 `StageLogWriter`、`StageRunner`、四个 stage（`separate`/`slice`/`convert`/`merge`）日志增强行为。
- 覆盖日志文件落盘、SSE 透传、失败/取消收尾、参数分组与路径格式化。
- 不覆盖第三方推理库内部 debug 日志，不改前端渲染协议。

---

## 2. 测试环境与公共准备

### 2.1 环境

- OS：Windows 10/11（与开发环境一致）
- Python：项目当前锁定版本
- 数据目录：`projects_meta/{project_id}`、`output/`、`input/`
- 测试框架：`pytest`

### 2.2 公共测试数据

- 项目 `project_id=test-song`
- 输入：
  - `input/test-song-mix.wav`
  - `input/test-song-reference.wav`
  - `input/test-song.lrc`
- 预置可用的 `separate`、`slice`、`convert`、`merge` 最小参数集

### 2.3 公共检查点

- 每个 stage 生成独立 log：`projects_meta/{project_id}/logs/{job_id}.log`
- 日志前缀仅使用：`[JOB] [INPUT] [PARAM] [CMD] [EXEC] [PROC] [OUT] [ERR]`
- 路径为相对路径且使用 `/` 分隔

## 3. Phase 完成后测试用例

### Phase 1：基础设施（`pipeline/stage_log.py` + 单元测试）

### P1-TC-001 参数分组过滤（LRC slice）
- **目标**：验证 LRC 模式下 `build_param_groups` 过滤 VAD 参数。
- **前置**：准备 `slice_mode=lrc` 参数样例。
- **步骤**：
  1. 调用 `build_param_groups(stage="slice", params=..., inputs=...)`。
  2. 检查返回 `wizard/advanced/defaulted` 分组内容。
- **预期**：
  - 不出现 `vad_threshold/min_speech_ms/min_silence_ms/speech_pad_ms`。
  - LRC 相关参数进入正确分组。

### P1-TC-002 advanced/defaulted 差异识别
- **目标**：验证非默认参数进入 `advanced`，默认参数进入 `defaulted`。
- **前置**：设置 `length_adjust=1.05`，`skip_existing=true`。
- **步骤**：
  1. 执行 `build_param_groups`。
  2. 读取分组结果。
- **预期**：
  - `length_adjust=1.05` 在 `advanced`。
  - `skip_existing` 仅出现在 `defaulted`（按 key 列出）。

### P1-TC-003 StageLogWriter 基础写入顺序
- **目标**：验证 `[JOB] -> [INPUT] -> [PARAM]` 顺序稳定。
- **前置**：`tmp_path` 下创建 writer。
- **步骤**：
  1. 依次调用 `job_header/inputs/params`。
  2. 读取 log 文件文本。
- **预期**：
  - 文件包含三个段落且顺序固定。
  - 每行带正确前缀。

### P1-TC-004 CMD 格式化输出
- **目标**：验证 `format_cmd` 产出三行信息。
- **步骤**：
  1. 调用 `stage_log.cmd(argv, cwd, python)`。
  2. 读取 log 文件。
- **预期**：
  - 含 `python=...`、`cwd=...`、`argv: ...` 三类 `[CMD]` 行。
  - `argv` 不被截断。

### P1 通过准则
- `tests/test_stage_log.py` 新增/更新用例全部通过。
- 无新增 lint 错误或类型错误。

---

### Phase 2：Runner 层（头尾、时间戳、排队时长）

### P2-TC-001 Job 头在入队前落盘
- **目标**：验证排队期间已可查看上下文。
- **前置**：模拟队列阻塞（延迟 worker 启动）。
- **步骤**：
  1. 调用 `run_stage` 触发任务入队。
  2. 在任务开始执行前读取 log。
- **预期**：
  - 已有 `[JOB] created_at/queued_at`。
  - 已有 `[INPUT]` 和 `[PARAM]`。

### P2-TC-002 queue_wait_ms 与 started_at 写入
- **目标**：验证 `_work()` 起始即写 `job_started`。
- **步骤**：
  1. 触发排队并制造可观测等待时间。
  2. 完成后检查日志。
- **预期**：
  - 存在 `[JOB] started_at=... queue_wait_ms=...`。
  - `queue_wait_ms` 为非负整数。

### P2-TC-003 失败收尾写入
- **目标**：验证 stage 抛错时日志闭环。
- **前置**：mock stage 抛异常。
- **步骤**：
  1. 执行 `run_stage`。
  2. 检查 job log 尾部。
- **预期**：
  - 有 `[ERR]` 失败摘要。
  - 有 `success=false` 的 `[JOB]` footer。

### P2-TC-004 取消收尾写入
- **目标**：验证取消路径仍写 footer。
- **前置**：可取消的长任务。
- **步骤**：
  1. 启动任务。
  2. 执行 `cancel_current`。
  3. 检查日志末尾。
- **预期**：
  - footer 状态为取消/失败语义之一。
  - 无中断导致的半截日志结构。

### P2 通过准则
- `tests/test_runner.py`（或等价 runner 集成测试）新增场景通过。
- 失败与取消场景均有 `[JOB]` 尾行。

---

### Phase 3：Subprocess 阶段（`separate` / `convert`）

### P3-TC-001 separate CMD/PROC/OUT 完整性
- **目标**：验证 subprocess 阶段日志完整链路。
- **步骤**：
  1. 执行 `separate`。
  2. 检查日志段落。
- **预期**：
  - 存在 `[CMD]` 三行。
  - 标准输出行进入 `[PROC]`。
  - Runner 末尾写 `[OUT] vocals/instrumental`。

### P3-TC-002 convert（slice_batch）上下文完整
- **目标**：验证切片批处理模式记录关键输入与参数。
- **前置**：`mode=slice_batch`，有 `manifest/slices_dir/reference`。
- **步骤**：
  1. 执行 `convert`。
  2. 检查 `[INPUT]`、`[PARAM]`、`[CMD]`。
- **预期**：
  - `[INPUT]` 含 `source_vocals/reference/slices_dir/manifest/output_dir`。
  - `[PARAM]` 分组符合规则。
  - `[OUT]` 含 `converted_count/total_count`。

### P3-TC-003 convert（full_track）分支正确
- **目标**：验证全轨模式输出字段契约。
- **前置**：`mode=full_track`。
- **步骤**：
  1. 执行 `convert`。
  2. 检查输出段。
- **预期**：
  - `[INPUT]` 使用 `output_path` 语义（而非 `slices_dir` 主路径）。
  - `[OUT]` 含 `full_track` 结果路径。

### P3-TC-004 兼容路径：`stage_log=None`
- **目标**：验证函数签名兼容旧调用方。
- **步骤**：
  1. 直接调用 `run_separate/run_convert(stage_log=None)`。
  2. 检查返回与进度行为。
- **预期**：
  - 不因缺少 `stage_log` 报错。
  - 旧 `_emit` 进度机制可用。

### P3 通过准则
- `separate`、`convert` 两阶段均能稳定输出 `[CMD]` + `[PROC]` + `[OUT]`。
- 兼容模式用例通过，无签名破坏。

### Phase 4：In-process 阶段（`slice` / `merge`）

### P4-TC-001 slice（LRC）EXEC 上下文
- **目标**：验证 `slice` 在无 subprocess 时使用 `[EXEC]`。
- **前置**：`slice_mode=lrc`，提供 `lrc` 文件。
- **步骤**：
  1. 执行 `slice`。
  2. 检查日志执行上下文段。
- **预期**：
  - 存在 `[EXEC] handler=scripts/slice-vocals-lrc.py mode=lrc`。
  - 关键输入（`lrc_path/vocals/output_dir`）可见。

### P4-TC-002 slice（VAD）参数可见性
- **目标**：验证 VAD 参数记录及模式隔离。
- **前置**：`slice_mode=vad`。
- **步骤**：
  1. 执行 `slice`。
  2. 检查 `[EXEC]` 细节。
- **预期**：
  - 含 `vad_threshold/min_speech_ms/min_silence_ms/speech_pad_ms`。
  - 不出现 LRC 专属字段。

### P4-TC-003 merge EXEC + PROC 链路
- **目标**：验证 merge 的执行说明与脚本输出透传。
- **步骤**：
  1. 执行 `merge`。
  2. 检查日志。
- **预期**：
  - `[EXEC]` 记录 profile 与关键增益参数。
  - 脚本 `on_line` 输出进入 `[PROC]`。
  - `[OUT]` 含 `merged_dir/vocals/mixed`。

### P4-TC-004 职责边界无重复
- **目标**：验证 Runner 与 Stage 无重复打印。
- **步骤**：
  1. 分别执行 `slice` 与 `merge`。
  2. 统计日志中的 `[INPUT]/[PARAM]` 和 `[EXEC]` 来源行。
- **预期**：
  - `inputs/params` 仅由 Runner 输出。
  - Stage 不再重复写同类摘要行。

### P4 通过准则
- `slice`、`merge` 日志均符合 `[EXEC]` 模式设计。
- 无重复段落，无字段缺漏。

### Phase 5：阶段验收与回归（测试补齐）

### P5-TC-001 SSE 回归
- **目标**：验证 SSE 协议未变更且 `log_line` 持续可用。
- **步骤**：
  1. 调用 stage API 并订阅 SSE。
  2. 捕获事件数据。
- **预期**：
  - 事件仍带 `project_id/stage/job_id/percent/message`。
  - `log_line` 存在时前端可直接显示增强日志行。

### P5-TC-002 取消回归
- **目标**：验证取消流程与历史行为兼容。
- **步骤**：
  1. 启动可取消阶段任务。
  2. 取消并观察 API 状态与日志。
- **预期**：
  - API 状态为取消语义。
  - 日志 footer 完整，`success=false`。

### P5-TC-003 现有 API 测试无回归
- **目标**：验证日志增强不影响既有接口行为。
- **步骤**：
  1. 执行相关 API 测试集。
  2. 比较变更前后结果。
- **预期**：
  - 关键 API 用例全部通过。
  - 失败时仅表现为日志内容差异，不应有行为回归。

### P5 通过准则
- 现有回归测试集通过。
- 新增测试在 CI 稳定通过。

## 4. 全部 Phase 完成后的整体测试用例

### ALL-TC-001 四阶段端到端日志闭环
- **目标**：验证从 `separate -> slice -> convert -> merge` 全链路日志完整。
- **步骤**：
  1. 以同一 `project_id` 顺序跑完四阶段。
  2. 检查四个 `job_id.log`。
- **预期**：
  - 每个日志均含头/过程/输出/尾。
  - 每阶段字段契约与方案一致。

### ALL-TC-002 模式矩阵覆盖
- **目标**：验证关键模式组合均可正确记录。
- **覆盖矩阵**：
  - `slice_mode`: `lrc` / `vad`
  - `convert_mode`: `slice_batch` / `full_track`
- **预期**：
  - 每种组合均输出正确的 `[INPUT]/[PARAM]/[CMD or EXEC]/[OUT]`。

### ALL-TC-003 前端可观测性验收
- **目标**：验证用户在 UI 中可直接定位核心信息。
- **步骤**：
  1. 打开 `StageLogPanel` 观察实时日志。
  2. 对照落盘文件检查一致性。
- **预期**：
  - UI 按原协议显示，无需前端改造。
  - 前缀语义清晰，能快速定位参数、命令、输出。

### ALL-TC-004 异常场景健壮性
- **目标**：验证失败、超时、取消等场景可诊断。
- **步骤**：
  1. 构造子进程失败、输入缺失、人工取消三类场景。
  2. 检查日志可读性。
- **预期**：
  - 均有 `[ERR]` 与 footer 收尾。
  - 可通过日志复现命令/定位输入参数问题。

### ALL-TC-005 日志规范一致性
- **目标**：验证格式规范在所有阶段统一。
- **检查项**：
  - 前缀集合是否受控
  - 路径是否为 repo 相对路径
  - 是否出现敏感字段（token/proxy/env）
- **预期**：
  - 无非法前缀、无绝对路径泄漏、无敏感信息。

### ALL-TC-006 性能与体量基线
- **目标**：验证日志增强不会显著拖慢阶段执行。
- **步骤**：
  1. 对比开启前后相同数据的执行时长。
  2. 统计单 job 日志文件大小。
- **预期**：
  - 执行时长增量在可接受范围（建议 <5%）。
  - 日志体量可控，未影响现有查看体验。

## 5. 执行建议（CI / 本地）

- **优先顺序**：Phase 1 单元 -> Phase 2~4 集成 -> Phase 5 回归 -> 全量 E2E。
- **建议命令**（按项目实际测试组织调整）：
  - `pytest tests/test_stage_log.py -q`
  - `pytest tests/test_runner.py -q`
  - `pytest tests/api/test_stage_sse.py -q`
  - `pytest tests -q`

## 6. 交付判定标准（Definition of Done）

- 每个 phase 的通过准则全部满足。
- 全部 phase 完成后的 `ALL-TC-001 ~ ALL-TC-006` 全通过。
- 测试结论可追溯到具体 `job_id.log` 与对应测试记录。

## 7. 测试执行记录模板

可为每个测试用例（如 `P3-TC-001`、`ALL-TC-004`）各记录一条：

```text
用例编号：
测试人：
测试日期：
测试结果：（通过 / 失败 / 阻塞）
缺陷单号：（无则填“无”）
备注：
```

示例：

```text
用例编号：P3-TC-001
测试人：张三
测试日期：2026-08-01
测试结果：通过
缺陷单号：无
备注：日志包含 [CMD]/[PROC]/[OUT]，与预期一致
```
